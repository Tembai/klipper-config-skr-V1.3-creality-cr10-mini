# Notes for future agent sessions

## Access
- Printer host: `192.168.1.222` (`.219` was previously used but is unreachable from this sandbox — the pi's IP appears to have changed), user `pi`. See `ssh_details.txt` for credentials (gitignored, not in repo).
- SSH via paramiko in Python, with `allow_agent=False, look_for_keys=False` — the local SSH agent key doesn't work in the sandbox, password auth is required.
- OctoPrint runs on the pi and only binds `127.0.0.1:5000` — reach it via `curl` executed over SSH, not directly from this machine. API key is in `ssh_details.txt`.
- Prefer OctoPrint's REST API (`/api/printer/command` for gcode, `/api/printer` for status, `/api/files` + `/api/job` for print control) over any custom direct-socket script (e.g. a `klipper_client.py` on the pi talking to `/tmp/klippy_uds`). The direct socket becomes unreliable (hangs/PipeTimeout) once OctoPrint's own web UI is open and connected — OctoPrint's own REST API doesn't have this problem since it's OctoPrint's established connection.
- Klipper's actual gcode log: `/tmp/klippy.log` on the pi. Useful for confirming what really happened (grep for `error`, `shutdown`, `Restarting`, `save_config`, etc.) since gcode execution continues on the printer even if an SSH exec_command channel times out/closes client-side — don't assume a command failed just because the SSH read timed out.

## Config file layout — important
- This repo's `printer.cfg` is included from the pi's real top-level config, `/home/pi/printer.cfg`, via `[include /home/pi/klipper-config-skr-V1.3-creality-cr10-mini/printer.cfg]`.
- `SAVE_CONFIG` always writes to `/home/pi/printer.cfg` (the stub with the `#*# <---- SAVE_CONFIG ---->` autogenerated block), NOT to this repo's tracked `printer.cfg`. This is expected — things like the `[bed_mesh default]` profile live only on the pi and are not meant to be synced into git.
- `SAVE_CONFIG` triggers a Klipper restart (clears homed state, resets heater targets to 0). Always re-home (`G28`) after calling it, and never call it mid-print.
- After `BED_MESH_CALIBRATE`, Klipper always prints "The SAVE_CONFIG command will update the printer config file and restart the printer." — this is just static informational text, NOT confirmation that a save/restart happened. `SAVE_CONFIG` must be called explicitly to persist.

## BLTouch (clone) findings
- This printer was migrated from a servo-based custom `[probe]` + deploy/stow/reset gcode macros to a native `[bltouch]` config section. The native driver is simpler and more reliable — prefer it over manual servo/probe macro setups for BLTouch clones.
- If the probe gets stuck reporting `TRIGGERED` (e.g. red LED blinking continuously), recover with `BLTOUCH_DEBUG COMMAND=reset` then `BLTOUCH_DEBUG COMMAND=pin_up`, then confirm via `QUERY_PROBE` that it reports `open`.
- Good `PROBE_ACCURACY` repeatability observed on this printer: range ~0.03–0.04mm, std dev ~0.01mm.

## Stepper noise
- CR10-to-Klipper migrations on this board can leave TMC2208 drivers in spreadCycle mode (loud/buzzy steppers) if `stealthchop_threshold` is `0` on some steppers but not others. Fix: set `stealthchop_threshold: 999999` (always-on stealthChop) consistently across all `[tmc2208 ...]` sections (X, Y, Z, extruder) rather than leaving some at `0`.

## Workflow gotchas
- Always preface git commit messages with `Generated: ` (e.g. `Generated: Fix noisy bed mesh...`).
- Don't create ad-hoc temp scripts inside this git repo for SFTP staging — if you must, delete them again once done (a `.tmp_*` file was left behind in a previous session and had to be cleaned up).
- `ssh_details.txt` and `lazygit.exe` are gitignored; don't try to track or reference their contents as if they were committed.
- `/tmp/klippy.log` on the pi accumulates config dumps across every restart. A naive `grep | tail` can show a mix of old and new values. Use `tac /tmp/klippy.log | grep -m1 -B2 -A2 '<setting>'` to reliably read only the most recent restart's values.
- Before sending `RESTART`, check the print is idle via OctoPrint's `/api/job` (`state` should be `Operational`), not just assumed.

## 2026-08-09 session: stringing/adhesion fix (Klipper motion limits + OrcaSlicer settings + PA)
- Symptom: severe uniform stringing and poor first-layer adhesion with OrcaSlicer, despite a known-good Cura 4.13.1 "CR10 Mini" profile working fine previously.
- Root cause investigation: compared the OrcaSlicer profile against Cura/Marlin's stock CR-10 Mini defaults (via Cura's `creality_base.def.json`/`creality_cr10mini.def.json` on GitHub). Found several mismatches:
  - Retraction was only 4.5mm (stock Cura/Marlin is ~6.5mm at 40-45mm/s).
  - Klipper's `[printer]` motion limits (`max_velocity: 100`, `max_accel: 800`, `max_z_accel: 80`, `square_corner_velocity: 2.0`) didn't match stock Marlin limits and were silently clipping travel moves — in particular OrcaSlicer's travel speed was set to 350mm/s, more than 2x both Cura's stock 150mm/s and Klipper's (old) 100mm/s ceiling, causing a timing/dynamics mismatch between what the slicer calculated for retraction-during-travel and what Klipper actually executed.
  - Updated `printer.cfg`: `max_velocity: 150`, `max_accel: 500`, `max_z_accel: 100`, `square_corner_velocity: 5.0`, added `max_extrude_only_velocity: 50` / `max_extrude_only_accel: 5000` to `[extruder]` — all matched to stock Marlin CR-10 Mini values. Deployed and verified 0 config errors.
- OrcaSlicer uses PrusaSlicer/Bambu-derived UI terminology, NOT Cura's — many settings are hidden unless the settings-panel mode dropdown is switched from Simple to Advanced/Expert. Verified exact field names/locations via the official wiki (`github.com/OrcaSlicer/OrcaSlicer/wiki`):
  - Printer Settings > Extruder > Retraction: Length, Retraction speed, **Deretraction speed** (`deretraction_speed`, 0 = same as retraction speed), **Travel distance threshold** (`retraction_minimum_travel` = Cura's `retraction_min_travel`, set to 1.5mm).
  - Printer Settings > Extruder > Z Hop: **Z-hop type** "Normal Lift" = Cura's plain vertical lift (already correct, no change needed); Z-hop height (`z_hop`) is low-priority/low-impact, 0.2-0.4mm both fine.
  - Process Settings > Others > Skirt: the Cura "skirt gap" equivalent is **Distance** (`skirt_distance`), set to 10mm; Loops (`skirt_loops`) = 3 matches Cura's `skirt_line_count`.
  - Process Settings > Strength > Infill (Advanced mode): Cura's "infill overlap" equivalent is **Infill Wall Overlap** (`infill_wall_overlap`), set to 30% to match Cura.
  - Cura's "avoid crossing perimeters"/combing and `travel_retract_before_outer_wall` have **no direct Orca equivalent/toggle** — Orca handles travel routing and pre-wall retraction internally; these were skipped rather than forced.
  - Process Settings > Speed > Travel: **Travel speed** lowered from 350mm/s to 150mm/s to match Klipper's `max_velocity` and Cura's stock value.
- After applying the above, a PA pattern test print showed a large improvement in quality (much better than before). Read the PA value off the printed pattern: test range was 0 to 1.2 in 0.05 steps (25 lines), user picked the second-to-last line = **1.15**. Set `pressure_advance: 1.15` in `[extruder]`, deployed, confirmed live via klippy.log.
- Net result: this combination (retraction length/travel-speed/motion-limit alignment with stock Marlin/Cura defaults + PA=1.15) fixed the stringing/adhesion regression. If tuning further, prefer keeping Klipper's `[printer]` motion limits in sync with whatever travel/print speeds are set in the slicer, rather than letting Klipper silently clip them.

## 2026-08-10 session: noisy bed mesh causing PA-test bed adhesion failures
- Symptom: a PA calibration test print (using PA=1.15 from the prior session) failed twice mid-print, with lines in the middle of the bed detaching/not adhering.
- Root cause: the saved `[bed_mesh default]` profile on the pi was stale (from 2026-08-08) and, more importantly, was baked from **single-sample** BLTouch probing (`samples: 1`). Re-probing the exact same physical point live showed real analog readings varying by up to ~0.13-0.2mm (e.g. `z=0.0675` vs `z=0.1975` at the identical X/Y) — consistent with this probe's documented ~0.18-0.35mm repeatability range in [troubleshooting_steps.txt](troubleshooting_steps.txt). A mesh built from single noisy samples shows a "salt and pepper" alternating +/- pattern between adjacent points rather than a smooth gradient — a good diagnostic signal to check for whenever adhesion fails in specific, localized print regions rather than uniformly.
- Fix 1 — sample averaging: added to `[bltouch]`: `samples: 2`, `samples_result: median`, `samples_tolerance_retries: 3`. This applies to *every* probing operation (bed mesh, z_offset calibration), not just one-off commands.
- Fix 1 gotcha — `samples_tolerance` must be realistic for the actual probe, not aspirational. Initially set to `0.05`, which is far tighter than this probe's real repeatability: `BED_MESH_CALIBRATE` retried the very first mesh point up to the max retry count, never converged, and raised `Probe samples exceed samples_tolerance` — a fatal error that **aborts the entire calibration**, leaving the old mesh in memory untouched. Fixed by raising to `samples_tolerance: 0.25` (based on the live noise range observed above plus the historical 0.18-0.35mm data), after which calibration completed cleanly with occasional single retries instead of hard failures.
- Fix 2 — a critical, easy-to-miss command-ordering gotcha (new lesson, expands on the "Config file layout" note above): `BED_MESH_CALIBRATE` calibrates a mesh into memory and makes it active for printing, but does **not** by itself get persisted by a later `SAVE_CONFIG` call unless you first explicitly run `BED_MESH_PROFILE SAVE=default` (or your profile's name). Without that explicit save step, `SAVE_CONFIG` just re-saves whatever profile data already existed in `/home/pi/printer.cfg`, silently discarding the freshly-calibrated mesh — 0 config errors, the file's mtime even changes, but the actual `#*# points =` data is byte-for-byte identical to before. Always run the full sequence in this exact order: `G28` → `BED_MESH_CALIBRATE` → `BED_MESH_PROFILE SAVE=default` → `SAVE_CONFIG`.
- Timing note: with `samples_tolerance_retries` set, `BED_MESH_CALIBRATE` over a 5x5 grid can take 90-150+ seconds depending on how many points need retries. When scripting this over the OctoPrint API with fixed `sleep()` calls between commands, budget generously (120s+) — commands queue and execute in order regardless of the client-side wait, but too short a wait risks polling for "done" before the real work finishes.
- Verification pattern used to confirm a real (not silently-failed) recalibration: after the full sequence, check (a) `grep -c 'Config error' /tmp/klippy.log` is 0, (b) `stat -c '%y' /home/pi/printer.cfg` mtime is newer than before, AND (c) the actual `#*# points =` values in `/home/pi/printer.cfg` differ from the pre-calibration values — (a) and (b) alone are not sufficient, since both can look fine even when the mesh silently wasn't updated.

## 2026-08-12 session: PA reading confounded by coarse bed mesh; increased mesh resolution
- Symptom: a fresh PA test print (range 0.3-0.92, step 0.02, PRINT_START loads the `default` bed_mesh profile via `BED_MESH_PROFILE LOAD=default`, no per-print recalibration) showed bad bed adhesion again around the PA=0.58-0.74 lines specifically, even after the 2026-08-10 sample-averaging fix — but this time the print didn't fail outright.
- Diagnosis method: downloaded the actual gcode file from OctoPrint (`/api/files` to list, `/downloads/files/local/<name>` to fetch) and grepped for `SET_PRESSURE_ADVANCE` to map PA values to X/Y coordinates. PA=0.58 starts at X≈135, PA=0.74 ends at X≈184, both at Y≈83.7-123.3 (OrcaSlicer's built-in PA calibration test lays PA values out left-to-right along X).
- Cross-referenced those X/Y coordinates against the (5x5, `probe_count: 5, 5`) saved `[bed_mesh default]` grid (points at X=20/77.5/135/192.5/250, Y=20/66.25/112.5/158.75/205): the X=135/192.5 columns at Y=66.25/112.5 read **+0.003 to +0.094**, while the X=20/77.5 columns (where PA=0.3-0.4 printed fine) read **-0.15 to -0.11** — a genuine ~0.15-0.24mm difference in compensated bed height between the two regions.
- Conclusion: since this shows up even with the already sample-averaged/statistically-robust probing from the prior session, it's very likely **real bed topology** (a genuine bump/dip or frame twist), not measurement noise — just one the coarse 5x5 grid wasn't resolving well via bicubic interpolation. A ~0.2mm unexpected nozzle-to-bed gap in one region is enough to explain localized adhesion failure independent of the true PA value, meaning **the PA value read directly off a test print can be confounded by bed mesh resolution/accuracy** — always sanity-check a PA test print's problem region against the current bed mesh matrix before trusting the reading at face value.
- Fix: increased `[bed_mesh]` `probe_count` from `5, 5` to `7, 7` (49 points, ~38x31mm cells instead of ~58x46mm) for finer compensation resolution. Also increased `[bltouch]` `samples` from `2` to `3` — `samples_result: median` with an even sample count (2) just averages the two readings; with 3 it becomes a true median that discards one outlier, a meaningfully more robust statistic for a probe with known ~0.13-0.35mm noise.
- Applied `pressure_advance: 0.62` (read from the same test print) per user request, flagged in the config comment as needing re-confirmation once the denser mesh is validated by a repeat test print.
- If adhesion issues persist even after the 7x7 recalibration in a way that still lines up with specific mesh regions, the next steps would be: physically re-check bed leveling/screws in that area, consider `probe_count` even higher (9x9) at the cost of much longer calibration time, or investigate frame/gantry rigidity in that region rather than assuming it's a probing/statistics problem at that point.
- Recalibrated with the new 7x7/samples=3 settings and re-checked the same X≈135-173, Y≈82-112 region against the new mesh: the local "bump" is still present (~-0.005 to +0.065 there vs ~-0.15 to -0.02 in the low-PA X=20-58 region, roughly a 0.1mm difference) but smaller than the ~0.15-0.24mm seen on the old 5x5 grid — consistent with a real, modest bed topology feature that the coarser grid was overstating via bicubic interpolation. **PA=0.62 should still be re-validated with a fresh print of the same PA test gcode** now that the denser mesh is active, to confirm the reading holds up.
- Timing correction to the note above: with a 7x7 grid (49 points) and `samples: 3`, full `BED_MESH_CALIBRATE` took **~10-11 minutes** (147 physical probes), far longer than the 5x5/samples=2 case. When scripting this, do not rely on a fixed `sleep()` guess to know when it's done — poll `grep -c 'probe at' /tmp/klippy.log` (expect `probe_count_x * probe_count_y * samples`) and `stat -c '%y' /home/pi/printer.cfg` (mtime only updates once `SAVE_CONFIG` actually completes) instead of trusting a script's "done" output, since gcode commands execute asynchronously on the printer regardless of the client-side wait duration.
